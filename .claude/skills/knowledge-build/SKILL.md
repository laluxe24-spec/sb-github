# ナレッジ化

ナレッジは2種類ある。1つの情報から、片方だけ作ることも、両方作ることもある。

| 種類 | 何のため | 保存先 | 手順 |
|---|---|---|---|
| 自分用 | りゅーじ君が恋愛・仕事・生活・考え方で実際に使う | `03_MyKnowledge/03_使える知識/<ジャンル>/` | `自分用.md` |
| 配信用 | 投稿のネタにする | `02_Knowledge/<ジャンル>/` | `配信用.md` |

**最重要ルール**: 集めた情報を、そのまま知識として保存しない。「Xで言われていた/本に書いてあった」は「正しい」ではない。必ず分析してから保存する。

**対象を指定された時**(「〇〇だけナレッジ化して」)は、1章の対象をそれだけに絞ってよい。

## 全体の流れ

```
新着を探す(1章)
  → 除外基準に当たるものを捨てる(2章)
  → 1件ずつ「自分用に使えるか」「配信に使えるか」を判断する(2章)
  → 自分用なら 自分用.md、配信用なら 配信用.md の手順で保存する(両方もある)
  → 記録する(4・5章)
  → QAのチェック(knowledge-checkスキル)
```

## 1. 新着の洗い出し

`02_Knowledge/_管理/knowledge_progress.json` の `processed_files` に無いものだけを対象にする。新着が無ければ何もせず終了してよい。

対象ソース:
- `01_Sources/02_X/data/@<各アカウント>/posts.json`(投稿。`id`で処理済み判定)
- `01_Sources/02_X/data/@kw1ew/スクショ/*.jpg`(会話スクショ、画像のまま読む。OCR不要)
- `01_Sources/03_TikTok/data/*/transcripts/*.md`(TikTokの文字起こし)
- `01_Sources/04_YouTube/data/*/transcripts/*.md`(YouTubeの文字起こし)
- `01_Sources/01_Kindle/data/*/本文.md`(本、`kindle/<本のタイトル>`の形でprocessed_files照合)

## 2. 除外と、どっち用かの判断

**除外基準(問答無用で対象外)**: 煽情的・操作的なテンプレ投稿(釣り文句集、「女性を洗脳する」系の商材宣伝、性的体験の実況)、怪しい商材の宣伝、MBTI・血液型などの根拠のない分類。信頼している発信者(乾さん・はやとさん)の内容でも、この基準に該当するもの(自著宣伝・講師紹介など技術的内容がないものを含む)は除外する。

除外しなかったものは、1件ずつ次で判断する。迷ったら両方作る。

- **自分用に使える**: りゅーじ君が実際の恋愛・仕事・生活・考え方で試せる(型・判断のしかた・言い回しなど)
- **配信用に使える**: 読者が「あるある」「知らなかった」と思える。投稿のテーマや切り口、セリフになる
- どちらにも使えない(情報が薄い・再現できない・ただの感想など)は保存しない

**ジャンル**は内容を見て決める(恋愛・心理学・営業・インテリア・マーケなど)。「この情報源はこのジャンル専用」と決め打ちしない。フォルダが無ければ作ってよい。

## 3. サブエージェントへの深掘り依頼(限定的にのみ使う)

通常の分析はこのスキルの中で完結させる。**次のような、明らかに専門的な深掘りが要る場合だけ**、Agent機能で専門サブエージェントを1つ呼び出してよい。

- 複数ジャンルにまたがる原理を統合する必要があり、このスキルの中での判断だけでは根拠の妥当性に自信が持てない
- 会話系で、人物像の解釈が複雑で、通常の分解手順では構造化しきれない

**呼び出す時のルール**:
- **1回の実行で、サブエージェントは合計2回まで**(それ以上必要に見えても、残りは`processed_files`に記録した上で次回以降に回す)
- 単純なノウハウ1件・会話1件・本1冊の通常処理では、絶対にサブエージェントを呼ばない
- 呼ぶ時は、対象の情報・すでに分かっていること・具体的に何を判断してほしいかを明記して依頼する
- サブエージェントの結果は、そのまま鵜呑みにせず、このスキルの基準(根拠レベルなど)に沿って統合する

## 4. 内部管理情報(見た目には出さない)

`02_Knowledge/_管理/knowledge_meta.json` に、項目ごとに以下を保存・更新する(既存エントリは消さず追加・更新する)。

```json
{
  "<項目タイトル>": {
    "use": "self"(自分用) または "post"(配信用),
    "kind": "action" または "conversation" または "summary",
    "source_group": "発信者名" または "本のタイトル" または "複数アカウント",
    "genre": "ジャンル",
    "file": "実際に保存したファイルパス",
    "sources": ["元になった投稿id・スクショファイル名・video_id・kindle本のタイトルなど(複数可)"],
    "matched_sources": ["複数アカウントの場合のみ:一致が確認できた発信元のリスト"],
    "confidence": "A〜D(ノウハウ・本)、またはhigh/medium/low(会話)",
    "status": "verified" または "tentative" または "hold" または "conflict",
    "hold_reason": "holdの場合のみ、保留理由を一言",
    "related": ["関連する他のKnowledge項目タイトル"],
    "sub_agent_used": true または false,
    "last_updated": "YYYY-MM-DD"
  }
}
```

保留(hold)にした項目は、本文の`.md`には書かず、ここにstatus:"hold"として記録するだけにする。

## 5. 完了処理・安全装置

- `knowledge_progress.json`の`processed_files`に、今回判断した分(保留・除外含む)を追記する
- 1回の実行で処理する新着は**最大100件**まで(それ以上あれば、処理した分だけ記録して終了し、残りは翌日以降に回す。無理に全部やろうとしない)
- 同じ`.md`ファイルを同じ実行の中で5回以上書き換えるような挙動になったら、設計ミスの兆候として処理を打ち切り、`/Users/ryuji/sb-mac-logs/knowledge-skipped.log`に状況を記録する
- **今回追加・更新したファイルと項目名を、`05_System/更新履歴.md`の一番上に日付見出し(`## YYYY-MM-DD`)付きで簡潔に追記する**(新しい日付ほど上に来るようにする。ファイルが無ければ新規作成)。りゅーじ君がObsidianで「今日何が増えたか」をすぐ確認できるようにするための場所。
- 最後に、今回やったこと(処理件数、種別ごとの内訳、新規/更新/保留、サブエージェント使用回数)を簡潔に出力して終わる

- 判断に自信が持てないものは無理にまとめず、`/Users/ryuji/sb-mac-logs/knowledge-skipped.log`に一言メモを残してスキップしてよい
