# ナレッジ化

**目的**: 情報をたくさん貯めることではなく、りゅーじ君が悩んだ・判断した・投稿を作ったときに使える状態にすること。単なる要約で終わらせず、必ず「どんな場面で」「どう考え/どう動けば」使えるのかという発動条件をつける。

**最重要ルール**: 集めた情報を、そのまま知識として保存しない。「Xで言われていた/本に書いてあった」は「正しい」ではない。必ず「分析→検証→条件付け」を通してから保存する。

**対象を指定された時**(「〇〇だけナレッジ化して」)は、0章の対象をそれだけに絞ってよい。

**保存先は情報源(誰の情報か)で決める**: 「行動系だからこのファイル」ではなく、「乾さんの情報だから乾式.md」「この本の情報だからそのタイトルの.md」というように、まず情報源の種別で保存先を固定する。一方、「内容をどう分析するか」(ノウハウとして分解するか、会話として構造分解するか、本として抽出するか)は、情報源では決め打ちせず、その都度内容を見て判断する。同じ発信元でも内容によって分析方法が変わって構わない。

## 全体の流れ

```
収集済みデータ(02_Sources、Xの投稿・kw1ewスクショ・TikTok文字起こし・Kindle本文)
  → 新着の洗い出し
  → 1章: 情報源の種別を判定し、保存先を決める
  → 2章: 内容を見て分析方法(行動系/会話系/要約系)を選び、分析する(必要な時だけサブエージェントに深掘りを依頼)
  → 3章の根拠レベル・除外基準を適用して保存
  → 内部管理・完了処理(4〜6章)
  → QAのチェック(knowledge-checkスキル)
```

## 0. 新着の洗い出し

`03_Knowledge/_管理/knowledge_progress.json` の `processed_files` に無いものだけを対象にする。新着が無ければ何もせず終了してよい。

対象ソース:
- `02_Sources/02_X/data/@<各アカウント>/posts.json`(投稿。`id`で処理済み判定)
- `02_Sources/02_X/data/@kw1ew/スクショ/*.jpg`(会話スクショ、画像のまま読む。OCR不要)
- `02_Sources/03_TikTok/data/*/transcripts/*.md`(文字起こし)
- `02_Sources/01_Kindle/data/*/本文.md`(本、`kindle/<本のタイトル>`の形でprocessed_files照合)

## 1. 情報源の種別判定・保存先の決定(最初に行う)

新着ごとに、まずどの情報源グループに属するかを判定する。

### 1-A. 専用ファイル対象の発信者(りゅーじ君が特に信頼してる個人)

現在の対象: **乾さん**(TikTok `@eigyou.inui`、ホームジャンル: `04_Sales`)、**はやとさん**(X `@kw1ew`、ホームジャンル: `03_Romance`)。今後対象が増える場合はこのスキル自体に追記する。

- **保存先**: `03_Knowledge/<その発信者のホームジャンル>/<発信者名>式.md`(無ければ新規作成)。1人につき1ファイルに統一する。内容が本来別ジャンルっぽい話題(例: 乾さんのメンタル管理の話)でも、ジャンルごとに分割せず、その発信者のホームジャンルのファイルの中に見出しを立てて収める。
- **採否判断**: 他の発信元との一致は不要。単独の発信でも、内容内でメカニズムの説明が筋通っているかどうかで採否・根拠レベル(3章)を判断してよい。ただし3章の除外基準に該当するものは対象外。
- **中身の書き方**: 内容がノウハウ・アドバイス系なら2-Aの方法、実際のやり取りなら2-Bの方法で分析してから書く。ファイル冒頭に`【リソース】`でその発信者を明記する。
- **並び順**: 新しい項目ほどファイルの上(見出し直後)に来るように追記する(下に積み足さない)。

### 1-B. 本(Kindle)

- **保存先**: `03_Knowledge/<内容に合うジャンル>/<本のタイトル>.md`(無ければ新規作成)。1冊の内容が複数ジャンルにまたがる場合は、ジャンルごとに別ファイルにする。
- **中身の書き方**: 2-Cの要約系の方法で分析してから書く。
- **並び順**: 本は章立てで書くため、新着順の並び替えは不要(本の構成に沿って書けばよい)。

### 1-C. 上記以外(複数アカウントを横断した経験則。例: X投稿型アカウント群)

- **保存先**: `03_Knowledge`ではなく`02_Sources/<該当ソース>/共通点メモ.md`(2026-09-18: 複数アカウントの経験則は学術的な検証を経ておらず、Knowledgeとして確定させるには根拠が弱いという判断のため)
- **採否判断**: 同じテーマを扱っている情報を発信元をまたいで集め、次のいずれかに当てはまるものだけを候補にする: 複数の発信元で一致/表現は違うが本質が同じ/条件は違うが共通する原則がある。1つの発信元だけの主張、他の情報と大きく矛盾、情報量が少ないものは採用しない。「事実を証明すること」が目的ではなく「複数の発信者から見ても共通しているパターンか」を確認する。個別のアカウント名までは本文に書かない。
- **仕上げ**: 根拠レベル(3章)は参考程度に付けてよいが、丁寧な実践用変換は不要(経験則メモとして簡潔に)。
- **並び順**: 新しい項目ほどファイルの上に来るように追記する。

## 2. 内容の分析方法(1章で情報源の種別を判定した後、内容を見て選ぶ)

同じ発信元・同じ保存先でも、内容によって以下のどの分析方法を使うかは変わってよい。1つの情報源から複数の要素(行動系と会話系など)が出てくる場合は、両方の方法を使い分けてよい。

### 2-A. 行動系(ノウハウ・アドバイス)の分析

「何をすべきか」のアドバイス・ノウハウ・テクニックを分析する。1件を単独で薄く知識化せず、メカニズムの説明が筋通っているか(1-Aの発信者)、複数の発信元で共通しているか(1-Cの場合)を確認した上で、実践できる形(条件・使う場面・使わない場面まで含めて)に整える。

### 2-B. 会話系(実際のやり取り)の分析

「正しいか」の検証ではなく、「なぜその返し・言い回しが面白い/効いているのか」を、りゅーじ君が別の場面でも再現できる形に分解する。**例外(必ず除外)**: 性的な体験報告・行為の詳細描写を含むやり取りは、会話の面白さやテンポが良くても対象から除外する(`processed_files`に記録だけして本文には残さない)。

各会話について、次の順で個別の型に分解する: ①元の返し ②何が面白いのか ③会話構造 ④心理・感情の動き ⑤言葉の選び方 ⑥テンポ・距離感 ⑦別の場面への応用 ⑧自分で使うための型(「相手が(条件)と言ってきたら、(この構造)で返す」というIF-THEN形式)。単なる「使えるフレーズ集」にしない。フレーズではなく構造を残す。

個別事例とは別に、**話し手ごとの人物像・スタイル総括**(ユーモアのセンス、言葉選びの傾向、真面目とふざけるの境界線、距離感の詰め方、NG・やらないこと)も育てる。矛盾する側面が見つかっても消さず両論併記する。中身のカード構成(タイトル/元ネタ/面白さ/会話構造/なぜ機能するか/再現分解/応用パターン/使える場面/使わない場面/具体例/関連Knowledge)は今まで通り。「セリフを覚える」ではなく「セリフを生み出す構造を覚える」ことが目的。

### 2-C. 要約系(本1冊)の分析

本の要約ではなく、「使うためのKnowledge」に変換する。本を読む→重要な考え方を理解する→使える原理を抽出する→**その原理が判断/行動/会話のどれに使えるかを項目ごとに判断する**→既存Knowledge(1-Bで決めた保存先ファイル)と統合する。「本だから判断」と決め打ちしない。1冊の中に、判断に使える内容・行動に使える内容・会話に使える内容が混ざっていることは普通にある。

- **判断**: 「この状況をどう捉えるか」「何を選ぶか」に使える
- **行動**: 「実際にどう動くか」に使える
- **会話**: 「実際に何を言うか・どうやり取りするか」に使える

1. 本全体の理解(何についてか、著者が最も伝えたいこと、全体を貫く考え方、各章の役割)
2. 章・テーマごとの解析(何を言っているか/なぜそう言っているか/どういう仕組みか/具体例/条件・例外。「著者の主張」と「AIの解釈」を混同しない)
3. 使えるKnowledgeの抽出(判断する時・悩んだ時・人間関係・行動を決める時などに実際に適用できるものを優先)
4. 項目ごとに判断/行動/会話のどれかを判定し、保存先ファイル(1-B)内でその種類ごとに見出しを立てて整理する
5. 発動条件をつける(「どんなケースになったらこれを使うか」を状況の構造で判断する)
6. 相談での使い方に変換する(判断型なら「AIが確認する質問」、行動型なら「具体的な行動」、会話型なら「型・言い回し」)
7. 既存Knowledgeとの統合(新規/補強/具体化/応用範囲拡張/使い分け/矛盾の両論併記/単なる重複の統合)
8. 使わないケースも明記(適用しないケース、誤用のリスク、適用前の確認事項)

出典(本のタイトル・著者)は必ず明記し、絶対に省略・推測で埋めない。確認できない出典を勝手に補完しない。

## 3. 除外基準・根拠レベル(すべての保存先に共通)

**ジャンル判定**: `03_Knowledge`内のどのジャンルフォルダ(`01_AI`, `02_Psychology`, `03_Romance`, `04_Sales`, `05_Marketing`, `06_Interior`など)に入れるかは、内容を見て判断する。「この情報源はこのジャンル専用」と決め打ちしない。該当フォルダが無ければ新しく作ってよい(`99_Other`は最終手段)。

**見た目は読みやすい文章形式を維持する。カード型データベースにはしない。**

**根拠レベル(行動系・要約系で使用)**:
- A: 心理学・行動科学の確立した理論や研究に対応
- B: 複数の情報源で独立して繰り返し主張されている経験則
- C: 一つの情報源のみだが、メカニズムの説明が筋が通っている経験則
- D: 根拠が弱い・個人差が大きい・再現性に疑問がある

**除外基準(問答無用で対象外)**: 煽情的・操作的なテンプレ投稿(釣り文句集、「女性を洗脳する」系の商材宣伝、性的体験の実況)、怪しい商材の宣伝、MBTI・血液型などの根拠のない分類。1-Aの信頼してる発信者(乾さん・はやとさん)の内容でも、この基準に該当するもの(自著宣伝・講師紹介など技術的内容がないものを含む)は除外する。

## 4. サブエージェントへの深掘り依頼(限定的にのみ使う)

通常の分析はこのスキルの中で完結させる。**次のような、明らかに専門的な深掘りが要る場合だけ**、Agent機能で専門サブエージェントを1つ呼び出してよい。

- 複数ジャンルにまたがる原理を統合する必要があり、このスキルの中での判断だけでは根拠の妥当性に自信が持てない
- 会話系で、人物像の解釈が複雑で、通常の分解手順では構造化しきれない

**呼び出す時のルール**:
- **1回の実行で、サブエージェントは合計2回まで**(それ以上必要に見えても、残りは`processed_files`に記録した上で次回以降に回す)
- 単純な行動系1件・会話系1件・要約1冊の通常処理では、絶対にサブエージェントを呼ばない
- 呼ぶ時は、対象の情報・すでに分かっていること・具体的に何を判断してほしいかを明記して依頼する
- サブエージェントの結果は、そのまま鵜呑みにせず、このスキルの基準(根拠レベルなど)に沿って統合する

## 5. 内部管理情報(見た目には出さない)

`03_Knowledge/_管理/knowledge_meta.json` に、項目ごとに以下を保存・更新する(既存エントリは消さず追加・更新する)。

```json
{
  "<項目タイトル>": {
    "kind": "action" または "conversation" または "summary",
    "source_group": "1-A(発信者名)" または "1-B(本のタイトル)" または "1-C(共通点メモ)",
    "genre": "保存先のジャンルフォルダ名",
    "file": "実際に保存したファイルパス",
    "sources": ["元になった投稿id・スクショファイル名・video_id・kindle本のタイトルなど(複数可)"],
    "matched_sources": ["1-Cのみ:一致が確認できた発信元のリスト"],
    "confidence": "A〜D(行動系・要約系)、またはhigh/medium/low(会話系)",
    "status": "verified" または "tentative" または "hold" または "conflict",
    "hold_reason": "holdの場合のみ、保留理由を一言",
    "related": ["関連する他のKnowledge項目タイトル"],
    "sub_agent_used": true または false,
    "last_updated": "YYYY-MM-DD"
  }
}
```

保留(hold)にした項目は、本文の`.md`には書かず、ここにstatus:"hold"として記録するだけにする。

## 6. 完了処理・安全装置

- `knowledge_progress.json`の`processed_files`に、今回判断した分(保留・除外含む)を追記する
- 1回の実行で処理する新着は**最大100件**まで(それ以上あれば、処理した分だけ記録して終了し、残りは翌日以降に回す。無理に全部やろうとしない)
- 同じ`.md`ファイルを同じ実行の中で5回以上書き換えるような挙動になったら、設計ミスの兆候として処理を打ち切り、`/Users/ryuji/sb-mac-logs/knowledge-skipped.log`に状況を記録する
- **今回追加・更新したファイルと項目名を、`07_System/更新履歴.md`の一番上に日付見出し(`## YYYY-MM-DD`)付きで簡潔に追記する**(新しい日付ほど上に来るようにする。ファイルが無ければ新規作成)。りゅーじ君がObsidianで「今日何が増えたか」をすぐ確認できるようにするための場所。
- 最後に、今回やったこと(処理件数、種別ごとの内訳、新規/更新/保留、サブエージェント使用回数)を簡潔に出力して終わる

## 置き場所の補足: 書き方・構成の知識は05_Marketingに集める

投稿の「書き方・構成・伸ばし方」(1行目の作り方、コメント欄への誘導、句読点の使い方など、プラットフォーム共通で使い回せるライティング技術)は、ジャンルを問わず`05_Marketing`に集約する。ジャンル別フォルダ(`03_Romance`・`06_Interior`・`04_Sales`など)には、そのジャンル固有の「何を言うか」の内容知識だけを置く。

理由: 「書き方」は恋愛でもインテリアでも共通して使える技術なので、ジャンルごとに分散させると同じ知見を何度も集め直すことになる。1箇所にまとめて、どのジャンルの発信をする時もそこを参照する運用にする。

新しくKnowledgeを追加する時は、内容が「書き方・構成」の話なのか「そのジャンル固有の内容」の話なのかをまず判断し、置き場所を間違えないようにする。
