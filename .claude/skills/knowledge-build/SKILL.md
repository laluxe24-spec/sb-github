# ナレッジ化

**目的**: 情報をたくさん貯めることではなく、りゅーじ君自身の成長と、発信のネタの両方に使える状態にすること。単なる要約で終わらせず、必ず「どんな場面で」「どう考え/どう動けば」使えるのかという発動条件をつける。

**最重要ルール**: 集めた情報を、そのまま知識として保存しない。「Xで言われていた/本に書いてあった」は「正しい」ではない。必ず「分析→検証→条件付け」を通してから保存する。

**対象を指定された時**(「〇〇だけナレッジ化して」)は、0章の対象をそれだけに絞ってよい。

**保存先は情報源(誰の情報か)で決める**: 「ノウハウだからこのファイル」ではなく、「乾さんの情報だから乾式.md」「この本の情報だからそのタイトルの.md」というように、まず情報源の種別で保存先を固定する。一方、「内容をどう分析するか」(ノウハウとして分解するか、会話として構造分解するか、本として抽出するか)は、情報源では決め打ちせず、その都度内容を見て判断する。同じ発信元でも内容によって分析方法が変わって構わない。

## 全体の流れ

```
新着を探す(0章)
  → 誰の情報か・どのジャンルかで保存先を決める(1章)
  → 情報の形に合った分析のしかたで分析する
       ノウハウ・アドバイス → ノウハウ.md
       実際の会話のやり取り → 会話.md
       本 → 本.md
  → 除外基準・根拠レベルを当てて保存する(3章)
  → 成長用のジャンルなら「りゅーじ君なら」をつける(5章)
  → プロジェクトと同じジャンルならネタ帳に切り口を足す(6章)
  → 記録する(7・8章)
  → QAのチェック(knowledge-checkスキル)
```

## 0. 新着の洗い出し

`02_Knowledge/_管理/knowledge_progress.json` の `processed_files` に無いものだけを対象にする。新着が無ければ何もせず終了してよい。

対象ソース:
- `01_Sources/02_X/data/@<各アカウント>/posts.json`(投稿。`id`で処理済み判定)
- `01_Sources/02_X/data/@kw1ew/スクショ/*.jpg`(会話スクショ、画像のまま読む。OCR不要)
- `01_Sources/03_TikTok/data/*/transcripts/*.md`(TikTokの文字起こし)
- `01_Sources/04_YouTube/data/*/transcripts/*.md`(YouTubeの文字起こし)
- `01_Sources/01_Kindle/data/*/本文.md`(本、`kindle/<本のタイトル>`の形でprocessed_files照合)

## 1. 情報源の種別判定・保存先の決定(最初に行う)

新着ごとに、まずどの情報源グループに属するかを判定する。

### 1-A. 専用ファイル対象の発信者(りゅーじ君が特に信頼してる個人)

現在の対象: **乾さん**(TikTok `@eigyou.inui`、ホームジャンル: `03_Sales`)、**はやとさん**(X `@kw1ew`、ホームジャンル: `02_Romance`)。今後対象が増える場合はこのスキル自体に追記する。

- **保存先**: `02_Knowledge/<その発信者のホームジャンル>/<発信者名>式.md`(無ければ新規作成)。1人につき1ファイルに統一する。内容が本来別ジャンルっぽい話題(例: 乾さんのメンタル管理の話)でも、ジャンルごとに分割せず、その発信者のホームジャンルのファイルの中に見出しを立てて収める。
- **採否判断**: 他の発信元との一致は不要。単独の発信でも、内容内でメカニズムの説明が筋通っているかどうかで採否・根拠レベル(3章)を判断してよい。ただし3章の除外基準に該当するものは対象外。
- **中身の書き方**: 内容がノウハウ・アドバイス系なら`ノウハウ.md`、実際のやり取りなら`会話.md`の方法で分析してから書く。ファイル冒頭に`【リソース】`でその発信者を明記する。
- **並び順**: 新しい項目ほどファイルの上(見出し直後)に来るように追記する(下に積み足さない)。

### 1-B. 本(Kindle)

保存先・書き方は`本.md`。

### 1-C. 上記以外(複数アカウントを横断した経験則。例: X投稿型アカウント群)

- **保存先**: `02_Knowledge`ではなく`01_Sources/<該当ソース>/共通点メモ.md`(複数アカウントの経験則は、Knowledgeとして確定させるには根拠が弱いため)
- **採否判断**: 同じテーマを扱っている情報を発信元をまたいで集め、次のいずれかに当てはまるものだけを候補にする: 複数の発信元で一致/表現は違うが本質が同じ/条件は違うが共通する原則がある。1つの発信元だけの主張、他の情報と大きく矛盾、情報量が少ないものは採用しない。「事実を証明すること」が目的ではなく「複数の発信者から見ても共通しているパターンか」を確認する。個別のアカウント名までは本文に書かない。
- **仕上げ**: 根拠レベル(3章)は参考程度に付けてよいが、丁寧な実践用変換は不要(経験則メモとして簡潔に)。
- **並び順**: 新しい項目ほどファイルの上に来るように追記する。

## 3. 除外基準・根拠レベル(すべての保存先に共通)

**ジャンル判定**: `02_Knowledge`内のどのジャンルフォルダ(`01_Psychology`, `02_Romance`, `03_Sales`, `04_Marketing`, `05_Interior`など)に入れるかは、内容を見て判断する。「この情報源はこのジャンル専用」と決め打ちしない。該当フォルダが無ければ新しく作ってよい(`99_Other`は最終手段)。

**見た目は読みやすい文章形式を維持する。カード型データベースにはしない。**

**並び順**: 発信者のファイルと共通点メモは、新しい項目ほど上に書く。本は章の順番のまま。

**根拠レベル(ノウハウ・本で使用)**:
- A: 心理学・行動科学の確立した理論や研究に対応
- B: 複数の情報源で独立して繰り返し主張されている経験則
- C: 一つの情報源のみだが、メカニズムの説明が筋が通っている経験則
- D: 根拠が弱い・個人差が大きい・再現性に疑問がある

**除外基準(問答無用で対象外)**: 煽情的・操作的なテンプレ投稿(釣り文句集、「女性を洗脳する」系の商材宣伝、性的体験の実況)、怪しい商材の宣伝、MBTI・血液型などの根拠のない分類。1-Aの信頼してる発信者(乾さん・はやとさん)の内容でも、この基準に該当するもの(自著宣伝・講師紹介など技術的内容がないものを含む)は除外する。

## 4. サブエージェントへの深掘り依頼(限定的にのみ使う)

通常の分析はこのスキルの中で完結させる。**次のような、明らかに専門的な深掘りが要る場合だけ**、Agent機能で専門サブエージェントを1つ呼び出してよい。

- 複数ジャンルにまたがる原理を統合する必要があり、このスキルの中での判断だけでは根拠の妥当性に自信が持てない
- 会話系で、人物像の解釈が複雑で、通常の分解手順では構造化しきれない

**呼び出す時のルール**:
- **1回の実行で、サブエージェントは合計2回まで**(それ以上必要に見えても、残りは`processed_files`に記録した上で次回以降に回す)
- 単純なノウハウ1件・会話1件・本1冊の通常処理では、絶対にサブエージェントを呼ばない
- 呼ぶ時は、対象の情報・すでに分かっていること・具体的に何を判断してほしいかを明記して依頼する
- サブエージェントの結果は、そのまま鵜呑みにせず、このスキルの基準(根拠レベルなど)に沿って統合する

## 5. 「りゅーじ君なら」をつける(成長用のジャンルだけ)

2章のジャンルの表で「つける」になっているジャンルのカードには、一般的な型の後に「**りゅーじ君なら**」の段落を足す。

- 先に`03_MyKnowledge/りゅーじのこと.md`を読む(背景・考え方・よくある悩み・得意不得意・目標)
- それをふまえて、「りゅーじ君の場合は、どんな場面で・どう使うといいか」を2〜3行で書く。一般論の言い換えにしない
- `りゅーじのこと.md`が無い、または必要なことが書いてない時は、想像で書かずにこの段落を省く

## 6. ネタ帳に切り口を足す(プロジェクトがあるジャンルだけ)

2章のジャンルの表でネタ帳があるジャンルは、投稿に使えそうなカードごとに、そのネタ帳の一番上に足す。**中身は書き写さない**(中身はナレッジ側にだけ置く)。

```
■ <ネタの名前>
テーマ: / 切り口: (NG行動・成功行動・意外な事実・女性側の受け取り方など)
フック案: (1行目の案)
元ネタ: <ナレッジのファイル名>「<カードの見出し>」
```

投稿に向かないカード(使い道が狭すぎる、炎上しそう、など)は足さなくていい。

## 7. 内部管理情報(見た目には出さない)

`02_Knowledge/_管理/knowledge_meta.json` に、項目ごとに以下を保存・更新する(既存エントリは消さず追加・更新する)。

```json
{
  "<項目タイトル>": {
    "kind": "action" または "conversation" または "summary",
    "source_group": "1-A(発信者名)" または "1-B(本のタイトル)" または "1-C(共通点メモ)",
    "genre": "保存先のジャンルフォルダ名",
    "file": "実際に保存したファイルパス",
    "sources": ["元になった投稿id・スクショファイル名・video_id・kindle本のタイトルなど(複数可)"],
    "matched_sources": ["1-Cのみ:一致が確認できた発信元のリスト"],
    "confidence": "A〜D(ノウハウ・本)、またはhigh/medium/low(会話)",
    "status": "verified" または "tentative" または "hold" または "conflict",
    "hold_reason": "holdの場合のみ、保留理由を一言",
    "related": ["関連する他のKnowledge項目タイトル"],
    "sub_agent_used": true または false,
    "last_updated": "YYYY-MM-DD"
  }
}
```

保留(hold)にした項目は、本文の`.md`には書かず、ここにstatus:"hold"として記録するだけにする。

## 8. 完了処理・安全装置

- `knowledge_progress.json`の`processed_files`に、今回判断した分(保留・除外含む)を追記する
- 1回の実行で処理する新着は**最大100件**まで(それ以上あれば、処理した分だけ記録して終了し、残りは翌日以降に回す。無理に全部やろうとしない)
- 同じ`.md`ファイルを同じ実行の中で5回以上書き換えるような挙動になったら、設計ミスの兆候として処理を打ち切り、`/Users/ryuji/sb-mac-logs/knowledge-skipped.log`に状況を記録する
- **今回追加・更新したファイルと項目名を、`05_System/更新履歴.md`の一番上に日付見出し(`## YYYY-MM-DD`)付きで簡潔に追記する**(新しい日付ほど上に来るようにする。ファイルが無ければ新規作成)。りゅーじ君がObsidianで「今日何が増えたか」をすぐ確認できるようにするための場所。
- 最後に、今回やったこと(処理件数、種別ごとの内訳、新規/更新/保留、サブエージェント使用回数)を簡潔に出力して終わる

## 注意

- 毎朝の自動実行ではBashツールが使えない設定なので、ファイルの読み書き(Read/Write/Edit/Glob/Grep)とAgent機能だけで完結させること
- 判断に自信が持てないものは無理にまとめず、`/Users/ryuji/sb-mac-logs/knowledge-skipped.log`に一言メモを残してスキップしてよい

## 置き場所の補足: 書き方・構成の知識は04_Marketingに集める

投稿の「書き方・構成・伸ばし方」(1行目の作り方、コメント欄への誘導、句読点の使い方など、プラットフォーム共通で使い回せるライティング技術)は、ジャンルを問わず`04_Marketing`に集約する。ジャンル別フォルダ(`02_Romance`・`05_Interior`・`03_Sales`など)には、そのジャンル固有の「何を言うか」の内容知識だけを置く。

理由: 「書き方」は恋愛でもインテリアでも共通して使える技術なので、ジャンルごとに分散させると同じ知見を何度も集め直すことになる。1箇所にまとめて、どのジャンルの発信をする時もそこを参照する運用にする。

新しくKnowledgeを追加する時は、内容が「書き方・構成」の話なのか「そのジャンル固有の内容」の話なのかをまず判断し、置き場所を間違えないようにする。
