# ナレッジのチェック

**役割**: 「正しいか間違っているかを裁く」のではなく、「解析係が作ったKnowledgeが、保存する価値のある形になっているかを確認する」こと。解析係の判断そのものを疑いすぎて何でもかんでも書き直さず、明らかにおかしい所だけ直す。

## やること

1. `git diff --stat HEAD -- 03_Knowledge/` と `git diff HEAD -- 03_Knowledge/` で、今回解析係が新規作成・追記した箇所を確認する(gitはまだcommitしていない前提。変更が無ければ何もせず終了)。
2. 追加・変更された各項目について、`knowledge_meta.json`の該当エントリと元ソース(スクショ画像・Xの投稿・TikTok文字起こし)を実際に読み直し、種類に応じて確認する。

### 会話系(`会話.md`)の確認項目
- 元のスクショの内容を誤解していないか
- 「面白さ」が単なる感想で終わらず、会話構造まで分解できているか
- 実際に別の状況へ応用できる形(型)になっているか、フレーズの丸暗記で終わっていないか
- 「なぜそうなるのか」(心理・テンポ・言葉選びなど)が説明できているか
- 後から読んだりゅーじ君本人が、実際の会話で使える形になっているか
- **注意**: りゅーじ君が良いと思って残した会話を、根拠が弱いという理由だけで削除・却下しない。ここでの品質チェックは「構造分解が甘くないか」であって「事実として正しいか」ではない。

### 行動系(`行動.md`)の確認項目
- `## <発信者名>式`の見出し(乾式・はやと式など)の下にある内容は、単一発信者由来として扱ってよい(複数アカウントとの一致は不要)
- それ以外の項目(見出しのない、複数アカウント横断のはずの内容)は、`knowledge_meta.json`の`matched_sources`を見て、複数の発信元に共通する要素を正しく統合できているか確認する(1つの発信元の意見をそのまま原則化していないか)。複数アカウントの経験則は`03_Knowledge`ではなく`02_Sources/<ソース>/共通点メモ.md`に置くべきものなので、`行動.md`に紛れ込んでいたら移動する
- 「女性は〜」「男性は〜」「必ず〜になる」のような過度な一般化になっていないか。必要なら「この条件では」に修正する
- 根拠レベル(A〜D)が実態と合っているか
- 既存の他項目とほぼ同じ内容を重複して書いていないか(重複していれば統合する)
- 既存Knowledgeと矛盾する場合、どちらかを消さずstatusを"conflict"にして、条件・文脈・根拠の違いをmeta.jsonに書き残す
- `knowledge_meta.json`の`genre`が、本文の内容と実際に合っているか(判定ミスがあれば正しいジャンルフォルダに移動する)

### 要約系(`判断.md`、本によっては`行動.md`/`会話.md`にも分解される)の確認項目
- `本文.md`を実際に読み直し、内容が本の主張を捻じ曲げていないか(無いことを付け足していないか)
- 単なる要約で終わらず、「使えるKnowledge」(発動条件・判断手順・具体例)まで落とし込めているか
- ジャンル分類が内容と合っているか
- 判断/行動/会話のどれに分類したかが、内容の実態と合っているか(本だからといって全部「判断」に入れていないか)
- 既存の`判断.md`の項目と重複・矛盾していないか(重複は統合、矛盾は両論併記)

### 共通
- `CLAUDE.md`・`03_Knowledge/01_AI/用語メモ.md`のスタイル方針(簡潔・初心者向け)に沿っているか
- ジャンル分類(置き場所)・型分類(判断/行動/会話)が適切か
- **出典・リソースが必ず明記されているか**(`【リソース】`または`→ リソース:`の形で、本のタイトル・Xのアカウント名相当・TikTokの発信者名などが書かれているか)。書かれていなければ追記する。ただし複数アカウントを横断分析した統合Knowledgeについては、個別のアカウント名までは書かない(内容の妥当性だけで判断するため、これは削除対象ではなく元々の仕様)
- 出典が実際に確認できないものを、推測で補完していないか

3. 軽微な問題(誤字、スタイル逸脱、置き場所の間違い、meta.jsonとの不整合など)は自分で直接修正してよい。
4. 「事実と違う可能性がある」「複数アカウント一致の判定が怪しい」など重めの問題は、直接消したり書き換えたりせず、`/Users/ryuji/sb-mac-logs/knowledge-review-report.md` に日付付きで一言メモを残す(次回人が見て判断できるように)。
5. 最後に、チェックした件数・直した件数・報告に残した件数を、会話系/行動系それぞれ簡潔に出力して終わる。

## 注意

- gitへのcommit/pushはしない(確認用の`git diff`/`git log`/`git show`の読み取りだけ使ってよい、それ以外のBash操作はしない)
- 新着(差分)が無ければ何もせず終了してよい
