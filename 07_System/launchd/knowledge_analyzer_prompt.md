## 1. 会話系(kw1ewのスクショ)の処理

**目的**: 「正しいか」の検証ではなく、「なぜその返し・言い回しが面白い/効いているのか」を、りゅーじ君が別の場面でも再現できる形に分解すること。りゅーじ君が良いと思って保存対象に残っているスクショは、根拠が弱いという理由だけで却下しない。

**例外(必ず除外)**: 上記の「根拠が弱くても却下しない」方針とは関係なく、**性的な体験報告・行為の詳細描写を含むやり取り**は、会話の面白さやテンポが良くても対象から除外する(Knowledgeにもmeta.jsonにも起こさない、`processed_files`に記録だけして終わり)。

個別事例の「型」だけでなく、**似た状況でなくても「kw1ewならこう返しそう」と想像できるレベルの人物像**も合わせて育てる(1-Aを参照)。

### 1-A. kw1ewの人物像・会話スタイル(総括)

`X_会話テクニック.md`の一番上に置く、事例が増えるたびに更新していく総括セクション。個別の「型」カードとは別に、次のような**キャラクター全体の傾向**をまとめる。

- ユーモアのセンス(どんなボケ・ツッコミが多いか、皮肉系か天然系かなど)
- 言葉選びの傾向(語彙・口調のクセ)
- 真面目になる場面とふざける場面の境界線
- 距離感の詰め方(初対面〜親しくなった後でどう変わるか)
- NG・やらないこと(下品すぎる、詮索しすぎる、など踏み込まない一線)

新しい事例を処理するたびに、この総括を「変わらない」「補強された」「新しい側面が見つかった」のどれかで更新する。矛盾する側面が見つかったら消さずに「〜な面もあれば、〜な面もある」と両方残す。

各スクショについて、次の順で個別の型に分解する。

1. **元の返し**: スクショに写ってる実際のやり取り(誰が何と言ったか)
2. **何が面白いのか**: 具体的にどこがウケている/効いているのか
3. **会話構造**: 相手の発言 → この返し、という流れのどこで何をしているか
4. **心理・感情の動き**: 相手や場の空気がどう動いたか
5. **言葉の選び方**: 使われてる言葉・言い回しの特徴
6. **テンポ・距離感**: 間の取り方、フォーマル/カジュアルの度合い
7. **別の場面への応用**: 同じ構造を別の状況で使うなら何が変わるか
8. **自分で使うための型**: 「相手が(条件・状況)と言ってきたら、(この構造)で返す」という、IF-THEN形式の再現可能なルールとして書く。抽象的な説明で終わらせず、りゅーじ君が後で実際に似た場面に遭遇した時、AI(このプロジェクトの担当セッション)に「こう言われたんだけど、kwならどう返す?」と相談すれば、このルールを当てはめてその場で返しを一緒に考えられるレベルの具体性にする。

単なる「使えるフレーズ集」にはしない。フレーズではなく構造を残す。

## 2. 行動系(7アカウントの投稿・TikTok)の処理

**目的**: 1投稿を単独で知識化しない。複数の発信者(アカウント)を横断して比較し、共通するパターンだけをKnowledgeにする。

1. 同じテーマを扱っている投稿を、アカウントをまたいで集める
2. 次のいずれかに当てはまるものは「統合Knowledge」の候補にする
   - 複数アカウントで一致している
   - 表現は違うが本質が同じ
   - 条件は違うが共通する原則がある
   - 既存Knowledgeと一致している
3. 次のいずれかに当てはまるものは「参考情報・保留」にする(確定Knowledgeにしない)
   - 1アカウントだけの主張
   - 他の情報と大きく矛盾する
   - 条件が特殊すぎる
   - 情報量が少ない
4. 「事実を証明すること」が目的ではない。「複数の発信者から見ても共通しているパターンか」を確認する

TikTok(`@eigyou.inui`単独アカウント)は他と横断できないので、その投稿内でメカニズムの説明が筋通っているかどうかで判断してよい。

## 3. Knowledgeの完成形(見た目)

**見た目は今までの読みやすい文章形式を維持する。カード型データベースにはしない。**

### 会話系(`03_Knowledge/03_Romance/X_会話テクニック.md`)
項目ごとに: タイトル / 元ネタ / この会話の面白さ / 会話構造 / なぜこの言い方が機能するのか / 再現するための分解 / 応用パターン / 使える場面 / 使わない方がいい場面 / 具体例 / 関連Knowledge
「このセリフを覚える」ではなく「このセリフを生み出している構造を覚える」ことが目的。

### 行動系(`03_Knowledge/03_Romance/X_行動テクニック.md`、TikTokは`03_Knowledge/04_Sales/`)
項目ごとに: タイトル / 共通している考え方 / 複数アカウントの共通点 / 統合した原則 / どういう状況で使うのか / 具体的な行動 / 例外・条件 / 関連Knowledge
個別アカウントの意見を並べるのではなく、共通部分を抽出して原則化する。根拠レベル(A〜D)は末尾に付ける。
- A: 心理学・行動科学の確立した理論に対応
- B: 複数の情報源で独立して繰り返し主張されている経験則
- C: 一つの情報源のみだが、メカニズムの説明が筋が通っている
- D: 根拠が弱い・個人差が大きい

両ファイルとも、出典アカウント名は書かず内容の妥当性だけで判断する。煽情的・操作的なテンプレ投稿(釣り文句集など)は対象から除外する。既存ファイルに項目があれば追記・更新、無ければ新規追加。

## 4. 内部管理情報(見た目には出さない)

`07_System/launchd/knowledge_meta.json` に、Knowledge項目ごとの内部情報を保存・更新する(無ければ新規作成)。

```json
{
  "<会話テクニック.md or 行動テクニック.md内の項目タイトル>": {
    "type": "conversation" または "action",
    "sources": ["元になったスクショファイル名 or 投稿id(複数可)"],
    "matched_accounts": ["行動系のみ:一致が確認できたアカウント名のリスト"],
    "confidence": "A〜D、または会話系ならhigh/medium/low",
    "status": "verified" または "tentative" または "hold" または "conflict",
    "hold_reason": "holdの場合のみ、保留理由を一言",
    "related": ["関連する他のKnowledge項目タイトル"],
    "last_updated": "YYYY-MM-DD"
  }
}
```

保留(hold)にした項目は、本文の`.md`には書かず、この`knowledge_meta.json`にstatus:"hold"として記録するだけにする。
